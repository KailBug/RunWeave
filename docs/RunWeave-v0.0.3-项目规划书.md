## 0. 本次修订的核心决定

1. 首版专注 MCP 执行层；自有 Agent Loop 和 Web 聊天界面后移。
2. 外部 Harness 负责推理与构造操作；RunWeave 接收明确的 operation，不解释自然语言任务。
3. 保留单体 Server、独立 Node 和明确协议，不引入微服务、消息队列或插件平台。
4. 明确幂等、未知结果、取消和重连对账；断线后不自动重跑。
5. 资源 URI 与资源版本分离，不把跨节点调度包装成代码自动同步。
6. Node 保留最终授权；文件 API 边界与进程权限分开，首版限定可信开发环境。
7. MCP 从第一条可运行链路开始接入，CLI 同期承担诊断、查询和本地审批。
8. 产品验证以真实客户端、真实双节点和故障场景为准，不以组件数量或未来架构规模为准。

## 1. 产品摘要

开发者的计算环境往往分布在笔记本、工作站和远程服务器上。代码、数据集和运行环境不一定在同一台机器：一个节点适合查看仓库，另一个节点拥有数据或专门的计算能力。

RunWeave 希望让 Agent 使用这些设备时，能够表达“需要什么能力、访问什么资源、执行什么操作”，再由执行层选择合法节点、请求本地授权并返回结果。

**核心价值是有约束的跨节点执行：能力匹配、数据局部性、节点授权和可追踪的执行生命周期。** 用户不必为每个调用手动指定物理路径或重新编写远程调用胶水，但仍负责准备节点、资源、程序和信任策略。

首版交付一个可被现有 Agent 挂载的 MCP 后端。长期可以提供自有 Harness，但它应作为同一执行服务的另一种调用方，不成为首版的开发前置条件。

RunWeave 不要求控制平面位于公有云；Server 可以部署在用户管理的本机、私有网络或服务器上。

## 2. 目标用户与使用边界

### 2.1 首要用户

拥有两台或更多开发设备、熟悉 CLI 和配置文件的独立开发者、研究者，以及由单一可信所有者管理节点的小型技术环境。

典型起点包括：远程开发测试、数据所在机器上的统计分析，以及有特定运行能力的工作站执行任务。首批验证使用非生产环境和受信任的项目代码。

### 2.2 当前不覆盖的用户需求

| 需求 | 首版边界 |
| --- | --- |
| 互不信任的团队成员共享节点 | 不提供多租户隔离或细粒度团队权限 |
| 任意不可信代码运行 | 不提供强沙箱；进程使用 Node 运行账号权限 |
| 生产敏感数据诊断 | 不作为首版承诺场景，需要更完整的隔离、输出和权限评估 |
| 消费者零配置设备协同 | 不提供移动 App、文件同步或自动发现全部资源 |
| 全自动安装训练环境 | 用户提前准备程序、依赖与数据；执行层不承担环境编排 |

MCP 是接入方式，不是获客结果。首版需要验证用户是否能配置成功、Agent 是否能正确构造请求，以及 RunWeave 是否减少了现有远程操作的负担；不预设零获客成本或企业采购成立。

## 3. 核心原则

**Reason globally：** 推理和任务推进由发起调用的 Harness 负责。首版 RunWeave 不保存推理上下文，也不自行生成下一步操作。

**Execute locally：** 操作在具有所需能力和资源的 Node 上运行，物理资源解析发生在 Node。

**Move computation to data：** 原始资源不被自动复制到控制平面；一次操作需要的资源必须在目标 Node 共址。

**Return bounded information：** 返回有界 observation 与 artifact 引用。文件读取、日志和产物内容均属于数据返回，需要明确授权。

**Make execution explainable：** 每次执行能够回答请求是什么、为何选择该 Node、是否授权、是否启动、结果是什么；无法确认时明确报告未知。

## 5. 核心对象与责任归属

| 对象 | 定义与首版责任 |
| --- | --- |
| Harness / Agent | 外部推理方，将用户目标转成明确操作并决定下一步 |
| ExecutionRequest | 一次操作、所需能力和资源、运行限制、幂等键 |
| Execution | 独立持久记录，关联请求、Node、状态、结果与事件 |
| Node | 提供本地执行能力，并保留最终授权权 |
| Capability | Node 可提供的操作或程序能力；不是资源可用性的替代品 |
| Resource | 逻辑 URI 标识的资源，如 repo://demo |
| ResourceLocation | 资源在某 Node 上的位置、版本证据与可用性；物理 root 留在本地 |
| Placement | 对合法候选的选择过程和解释；首版是规则与纯函数，不是独立服务 |
| Policy / Approval | 本地允许、拒绝、等待人工决策；审批绑定具体执行 |
| Observation / Artifact | 有界结果信息与可授权读取的产物引用 |

Task 在首版只通过可选 `correlation_id` 关联多次 execution；它不代表 RunWeave 拥有一个持续推理的任务。调用方退出后，已经提交的 execution 可继续；无人继续调用时不会产生新的 execution。

Node 只指执行节点。CLI、MCP 客户端和未来 Web 是接入界面，不建模为需要注册心跳的 Interaction Node。

## 6. 架构与依赖边界

### 6.1 部署形态

采用一个仓库、一个 Go module、一个 `runweave` 二进制，以子命令启动不同角色。

Server 提供认证 HTTP 管理 API 和 Node WebSocket；Node 主动建立出站连接。现有 Harness 启动 `runweave mcp` stdio 薄代理，通过认证 HTTP API 访问 Server。代理没有自己的执行数据库和调度逻辑。

Server 使用本机 SQLite，Node 使用本地 SQLite 保存接收记录、审批和结果；stdout/stderr 与产物落 Node 文件。Server 与 Node 状态目录分别有 daemon 独占锁，防止同一目录被多个执行进程同时使用。

### 6.2 模块职责

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| contract / protocol | 请求、结果、错误码、网络消息与版本 | 网络连接、数据库、业务调度 |
| server | 统一执行入口、placement、状态转换、连接管理 | 本地程序启动、物理路径解析 |
| node | 资源解析、本地策略、审批消费、进程与文件操作 | LLM 推理、跨节点调度 |
| store | 显式 SQL、事务、迁移与查询 | 通用 Repository 框架和调度决策 |
| api / mcp / CLI | 认证和协议适配、结果展示 | 各自复制执行、取消或幂等规则 |

Server 的 Submit、Get、Cancel 是相应执行用例的唯一业务路径。状态变更集中管理，MCP 适配层不能直接操作数据库或 Node。Placement 使用明确输入快照；Node 不依赖 Server 内部实现。

不为每个产品名词建立接口框架。优先使用具体 Go 类型，只有进程控制、连接发送等真实边界使用小接口。新增目录应服务已有代码，不能为了未来扩展提前放置大量空壳。

### 6.3 技术基线

沿用 Go、标准库 HTTP/日志/进程管理、官方 MCP Go SDK、一个 SQLite 驱动和一个 WebSocket 库。配置使用带版本的 YAML，凭据通过受限文件或环境注入。

依赖具体版本在开工阶段锁定并验证；SQLite 驱动沿用实施规划中优先评估纯 Go 驱动的选择。不引入 Redis、NATS、Kafka、Kubernetes、ORM 基类或 DI 容器。

## 7. 执行请求和资源一致性

### 7.1 明确操作契约

请求包含 `request_id`、可选 `correlation_id`、`requirements`、`operation` 和 `timeout_ms`。自然语言说明可用于展示，不作为运行依据。

以下为设计样例；revision 中的占位值需由实际版本替换。

```json
{
  "request_id": "demo-test-001",
  "correlation_id": "demo-001",
  "requirements": {
    "capabilities": ["process.exec", "python"],
    "resources": [{"uri": "repo://demo", "revision": "git:<full-commit>", "clean": true}],
    "os": "linux"
  },
  "operation": {
    "kind": "process.exec",
    "program": "python",
    "args": ["-m", "pytest", "-q"],
    "cwd": {"resource": "repo://demo", "relative_path": "."}
  },
  "timeout_ms": 120000
}
```

Node 将 program 标识映射到已配置的本地程序，参数作为 argv 传递，不默认通过 shell。跨资源路径使用显式 `{resource, relative_path}` 参数对象，不在任意字符串中替换 URI。Server 和 Node 都校验操作中引用的资源已经声明且可访问。

文件操作只接受资源和相对路径。程序本身仍可能访问运行账号有权访问的其他路径；逻辑 URI 不是进程隔离机制。首版不允许调用方任意注入环境变量，子进程不继承 Node 连接 token 环境项。

### 7.2 同一 URI 不代表内容相同

资源位置包含 revision 证据。需要指定版本的仓库操作检查完整 commit 和干净工作树；数据集版本由所有者维护清单并标明证据来源。缺少证据时不能声称精确匹配。

未指定 revision 的请求可访问当前内容，但结果记录实际版本或 unknown。两节点上的同一 URI 不会自动同步；A 修改代码后到 B 验证，必须由操作者先准备一致内容。

首版复现 Demo 排除子模块、LFS、缓存差异和并发外部编辑。版本检查提供执行证据，不替代强快照隔离或完整环境复现。

## 8. Placement 规则

1. 根据认证身份确定可访问的 Node 和资源。
2. 过滤协议不兼容、未认证、未完成对账、离线及能力/OS 不符的节点。
3. 检查所有必需资源是否在同一 Node 共址，且满足版本条件。
4. 应用 Server 已知的静态权限限制，最终策略由 Node 再确认。
5. 仅保留空闲执行槽；合法候选优先用户偏好，再按 node_id 字典序选择。
6. 事务中再次检查并占槽、保存派发意图；竞争失败可重新选择尚未派发的合法候选。

所有必需能力、资源和权限都是硬约束，不能为提高成功率而降级。全部忙返回 NODE_BUSY；没有合法位置返回 NO_MATCHING_NODE 和可公开的原因。首版没有等待队列或自动资源迁移。

Heartbeat 只用于在线判断，不作为性能或延迟排名。Trace 保留约束、候选快照版本、排除原因、选择结果与规则版本。

## 9. 执行状态与故障契约

| 状态 | 含义 |
| --- | --- |
| CREATED | 已持久化，尚未记录派发意图 |
| DISPATCHING | 已占槽并记录意图，可能已到达 Node |
| WAITING_APPROVAL | Node 已记录请求，尚未启动 |
| RUNNING | Node 已确认启动 |
| UNKNOWN | 无法确认启动、运行或结束事实；不是失败终态 |
| 已知终态 | SUCCEEDED、FAILED、REJECTED、CANCELLED、TIMED_OUT、EXPIRED |

`cancel_requested` 只表示取消意图。只有确认停止后才报告 CANCELLED；完成与取消竞争时保留 Node 确认的真实结果。审批有独立有效期，运行 timeout 从进程执行阶段计时。

Server 以 `(principal_id, request_id)` 保证幂等提交：同键同内容返回原 execution，同键不同内容返回 IDEMPOTENCY_CONFLICT。Node 在启动前持久化接收记录与启动意图，重复派发不能重复启动。

数据库提交与 OS 启动无法构成一个原子事务。崩溃窗口内不能证明未启动时，报告 UNKNOWN，不自动重跑，也不承诺 exactly-once。防重记录有保留窗口，首版默认 30 天；人为删除状态不在防重保证内。

| 故障 | 必须行为 |
| --- | --- |
| 提交响应丢失 | 使用原 request_id 取回原记录 |
| 派发或启动确认丢失 | 查询和对账，不自动新建执行或换节点重跑 |
| Node 断线、daemon 仍活着 | 本地 timeout 继续有效，结果本地保存；Server 保留未知执行槽 |
| Server 重启 | 重新认证与对账，不能把内存空状态当作空闲 |
| Node 重启 | 检查 journal 与残留作业，未核实前不可调度 |
| 离线时取消 | 保存意图并报告未确认；重连后先处理取消和对账 |
| 存储不可写 | 拒绝启动新作业；无法可靠记录的结果不得伪装成功 |

一 Node 一槽包含等待审批和未解决的 UNKNOWN。已知结果本地保存并补报，Server 在状态与事件事务提交后确认接收。失联后追求明确证据，不靠乐观重试维持表面可用性。

Linux 作业使用受管理进程组，取消和超时须回收进程、子进程、管道与句柄。首版不支持主动 daemonize、setsid 或逃离进程组的作业；Node 崩溃后无法确认残留已清理时保持隔离，不能只根据可复用的 PID 判断。

## 10. 协议、身份与审批

Server–Node 使用有版本的 JSON 消息，携带消息 ID、连接 epoch、执行 ID 和 payload。最小协议覆盖注册、心跳、派发、审批等待、启动、结果、取消、查询、对账、结果 receipt 和产物读取。

每次认证连接产生新 epoch，旧连接不得更新新会话或接收新派发。协议版本独立于软件版本；未知操作与必填字段缺失直接拒绝，可选扩展字段按明确兼容规则处理。

Node token 与调用方 token 分离，管理员预创建 Node 身份并绑定凭据；支持撤销。Server 存高熵 token 摘要，本地保存原凭据时限制权限，日志不记录秘密。非 loopback 通信强制 TLS 验证。

派发中的 principal_id 来自 Server 认证上下文，不能信任 MCP 参数自报身份。Node 信任已配置 Server 的身份声明，同时保留本地最终否决权。

| 操作 | 默认授权 |
| --- | --- |
| 发现已发布元数据 | 在认证和访问范围内允许 |
| 未配置资源或程序 | DENY |
| fs.list / fs.read | 只有明确允许内容返回的资源才可 ALLOW |
| process.exec | ASK；所有者可为可信项目显式配置 ALLOW |
| 原始日志/产物读取 | 未授权则 DENY，每次读取复核策略 |

本地 CLI 审批展示拟执行程序、参数、cwd、资源与限制，绑定 execution_id、Node、请求摘要、映射/策略版本和有效期。改变请求或版本使审批失效；DENY 不可被 approve 覆盖。

审批 CLI 通过 Node store 的短事务写决策，只有 daemon 消费决策和启动进程。MCP 不提供批准工具。这防止远程调用方自行放行，不抵御同一 OS 账号下的恶意本地进程。

## 11. 信息返回与安全承诺

**隐私承诺：原始资源不被自动复制到控制平面；返回内容遵守配置的输出策略。** 日志、指标、文件内容和 artifact 都可能含敏感信息，数据局部性不能证明零外泄。

默认自动返回状态、退出码、耗时等小结果，stdout/stderr 留在 Node。结果是客观数据和简短机器生成摘要，不额外调用 LLM；没有报告解析器时不生成未经证实的业务结论。

文件 API 必须限制资源根目录，处理路径穿越与符号链接竞态。进程运行权限等于 Node 账号权限；cwd、程序名称白名单或禁用 sudo 都不能构成强沙箱。pytest 和解释器也属于代码执行。

Artifact 使用不透明 ID，元数据含所属 execution、Node、大小、类型、过期和截断情况；读取按 ID、offset、limit 授权。离线与过期分别返回 ARTIFACT_UNAVAILABLE、ARTIFACT_EXPIRED，不承诺永久可读。

日志和输出受配额控制；到达日志上限后继续排空管道并丢弃超额内容，不能因停止读输出导致作业死锁。清理不删除运行中产物或未确认的结果 journal。

Mutation 默认 coverage=unknown；可选 Git 比较只能标 best_effort，不能以空数组表示已经证明无副作用。详细默认限额以实施规划为基线，在测试中调整并记录。

## 12. MCP 与 CLI 产品交互

| MCP 工具 | 功能 |
| --- | --- |
| runweave.list_nodes | 发现授权范围内的节点、能力与状态 |
| runweave.list_resources | 发现资源、位置与版本证据 |
| runweave.execute | 持久提交明确操作并返回 execution_id |
| runweave.get_execution | 获取当前状态、审批提示、结果与轮询建议 |
| runweave.cancel_execution | 请求取消并区分是否已确认停止 |
| runweave.read_artifact | 读取已授权的有界产物片段 |

提交工具不等待远程长任务结束；原 MCP tool-call 的取消或客户端退出，不自动撤销已经提交的 execution。首版用普通工具实现持久句柄与查询，不依赖 MCP Tasks 扩展。

MCP 适配使用 inputSchema、outputSchema、structuredContent 和精简文本兼容表示；工具 hint 不承担权限判断。先验证一个具体客户端与版本，再增加兼容声明。

CLI 至少支持服务启动、节点连接与列表、身份创建/撤销、资源列表、执行提交/查询/取消、本地审批及产物读取。MCP 与 CLI 共用 Server API；诊断不能依赖模型是否愿意正确调用工具。

## 13. 存储、可观察性与维护

Server 持久化节点、资源位置、执行、事件、认证主体和 schema 版本；Node 持久化接收执行、审批、产物索引与 schema 版本。不建立未实现的 Agent 或 TaskGraph 表。

状态与事件同事务提交，网络等待和进程等待不放进事务。SQLite 使用本机磁盘、短写事务和受控并发；不依赖共享网络盘或多 Server 并发写同一状态。

事件用于排障和审计事实记录，不是 Event Sourcing。首版直接查询持久事件，无需 EventBus 框架。执行详情能展示为什么选择此 Node、当前阻塞在哪里以及下一步如何处理。

必须随发布维护请求/结果示例、协议兼容说明、SQL 迁移、故障测试、配置示例、备份恢复和排障文档。备份采用已验证的一致性流程，不能运行中只复制主数据库而遗漏 WAL。

## 14. 首版 Demo 与成功标准

### 14.1 三个递进 Demo

**Demo A：单节点受控执行。** 现有 Harness 发现样例仓库、读取授权信息、提交测试，Node 所有者批准后执行，客户端查询退出码和允许返回的日志。

**Demo B：能力与资源路由。** 两台 Node 连接，目标数据只在 B；不指定 B，RunWeave 根据实际资源与能力选中 B，并解释 A 被排除的原因。版本或能力不符时明确拒绝。

**Demo C：同一外部任务中的跨节点操作。** 先在 A 查看仓库，再在 B 对本地数据运行预先准备好的脚本，Harness 综合结果。多次 execution 共用 correlation_id，但 RunWeave 不维护推理循环。

涉及同一代码时由操作者事先准备同 revision 的干净工作树；Demo 不包含透明修改同步。基础路由验证不强制 GPU；若声称支持 CUDA 训练，需要另做真实 GPU 验证。

### 14.2 成功标准

| 标准 | 通过条件 |
| --- | --- |
| S1 接入成立 | 一个记录了版本的真实 MCP 客户端能发现、提交、查询和取消 |
| S2 多节点成立 | 两个真实 Linux Node 同时连接且具有不同资源或能力 |
| S3 路由成立 | 硬约束不降级、选择可解释、资源版本不静默替代 |
| S4 授权成立 | 未批准不启动，过期/变更审批失效，Node 保留否决权 |
| S5 生命周期成立 | 重复消息不重复启动；模糊状态报告 UNKNOWN，断线不自动重跑 |
| S6 进程控制成立 | 超时、取消及受管理子进程回收通过真实测试 |
| S7 信息边界成立 | 文件、输出、产物授权与配额可验证，限制不被夸大 |
| S8 可维护交付成立 | 干净安装、迁移/恢复、排障和完整测试证据可交接 |

首发须通过实施规划 A01–A16 的全部适用要求；这些是计划中的验收门槛，目前尚无通过记录。

## 15. 开发策略与长期演进

按契约与技术验证、MCP 单节点链路、受控进程、双节点路由、故障闭环、输出与发布的顺序推进。首条链路就包含基本认证、持久请求与资源约束；安全和幂等不留到收尾补做。

半年投入优先完成可用首版，再做试用反馈、修复、恢复演练和维护。具体阶段及验收映射见半年规划，不因有六个月时间就预先增加半年份的功能。

| 后续方向 | 现在保留的边界 | 启动条件 |
| --- | --- | --- |
| 自有 Harness | 不依赖 MCP 的执行服务、correlation_id | 执行层已可用，用户确需自有任务体验 |
| Windows Node | 平台进程实现与协议分离 | 原生进程树、路径和服务生命周期验证通过 |
| 新操作/沙箱 | 明确 operation、capability 与结果契约 | 存在第二种真实执行需求 |
| PostgreSQL / HA | 聚合 SQL、稳定身份、状态与故障语义 | 实测单机瓶颈或明确部署要求；需要专门设计 |
| 对象存储 | Artifact ID 与读取授权分离 | 本地留存和传输成为实际问题 |
| 工作流/自动恢复 | Execution 独立记录、未知状态可表达 | 有真实依赖、重试与补偿语义 |
| 团队权限 | 认证主体、Node 归属和本地授权 | 出现互不信任主体，不将单用户模式直接宣传为企业隔离 |

这些方向没有承诺的软件版本或日期。新增机制应由已观察到的需求触发，不由预设路线图自动触发。

## 16. 架构不变量与修订追踪

1. 推理方构造操作，RunWeave 不暗中引入推理循环。
2. 执行语义与执行位置分离，物理资源映射由 Node 负责。
3. 所有接入方式共用执行服务和状态转换规则。
4. Node 保留最终授权；认证、授权、用户审批不是同一件事。
5. Execution 不依赖调用方会话存续，Task 推进仍由调用方负责。
6. 不确定的执行事实必须能够表示，不能用自动重试掩盖。
7. 资源身份不等于版本一致，数据局部性不等于数据保密。
8. 结果有界、产物可授权读取、状态变化可追踪。
9. 协议和磁盘 schema 有版本，内部包允许按实际需求重构。
10. 首版保持单体和少量明确边界，不预建扩展框架。
