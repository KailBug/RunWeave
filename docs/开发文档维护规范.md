# 开发文档维护规范

状态：生效。生效与更新日期：2026-09-10。适用范围：RunWeave 全部开发工作。维护责任：当前工作项开发者；阶段验收与发布由项目维护者核对。

## 1. 目的与约束

开发文档用于说明系统实际如何工作、为何这样设计、如何验证与维护，以及下一步还缺什么。文档与代码一起维护、一起评审、一起交付，不等到发布前集中补写。

本规范结合常见工程实践制定，是 RunWeave 的项目约定，不宣称存在一套适合所有项目的强制行业文档格式，也不表示已经通过某项标准认证。

全部新开发文档放在仓库 `docs/` 下，即当前工作区 `D:\RunWeave\docs`。正文采用简体中文和 UTF-8 Markdown；示例代码、命令、协议字段、依赖名称与必要术语保留原文。配套图片和脱敏证据同样放在本目录；构建缓存、大量原始日志和含凭据资料不得入库。

根目录既有文档按用户约定属于总体规划，不列入开发文档。即使其标题带有“实施”“任务清单”或“验证记录”，也不据此自动迁移或重新分类。后续开发事实在 `docs/` 中维护并引用必要背景。根目录 README 和 AGENTS 仅承担项目入口、导航及协作规则职责。

## 2. 信息职责与一致性

| 信息 | 权威落点 | 维护原则 |
| --- | --- | --- |
| 产品目标、首版范围、长期方向 | 根目录总体规划及用户明确决定 | 不因实现便利而静默改变范围 |
| 当前架构和执行语义 | `docs/设计/` | 区分目标设计与实际实现；变更同步说明差异 |
| 重要选择及理由 | `docs/决策/` 的 ADR | 保存当时背景与取舍；后续决定显式替代 |
| 对外接口、配置和错误码 | `docs/参考/`，关联 schema/代码 | 每项定义只维护一处正文，其余页面链接引用 |
| 操作方法 | `docs/指南/` | 给出前提、命令、预期结果和已知限制 |
| 测试事实、兼容性结论 | `docs/验证/` | 有环境、版本、步骤和实际证据，不从局部结果推断全局 |
| 当前进展和待办 | `docs/进度/开发进度.md` | 以工作项和出口条件推进，链接设计和验证，不复制全文 |
| 对使用者有意义的变化 | `docs/发布/` | 按版本汇总行为变化、兼容性和迁移要求 |

发现代码、接口说明和规划不一致时，先确定这是实现缺陷、文档过时还是已授权的设计调整，再修正相应部分。代码可证明当前行为，但不自动证明该行为符合预期；规划也不能证明功能已存在。不能通过改写验收条件把未通过包装成通过。

## 3. 何时必须新增或更新文档

下表适用于 P0–P5 及后续开发。“同步”指同一工作项交付内完成；可以分多个提交，但使用 PR 时应在同一 PR 内完成关联变更。

| 触发事件 | 必需文档动作 | 完成时点 |
| --- | --- | --- |
| 开始一个功能或阶段 | 明确目标、范围、不做事项、依赖和可检查的验收条件；复用已有清单并补充具体差异 | 实现前 |
| 新增或调整模块边界、技术栈、数据归属、持久化/故障语义或安全边界 | 更新设计；有显著取舍或长期影响时新增 ADR，记录选择依据与影响 | 依赖该决定的实现前记录；交付时核对实际落地 |
| 新增或修改 MCP 工具、HTTP API、Node 消息、配置项或错误码 | 更新参考定义、合法/非法示例、默认值、限额、权限、错误行为和兼容性 | 同步交付 |
| 修改数据库 schema、状态目录布局或存储格式 | 更新数据说明、迁移步骤、备份/恢复条件和不可逆限制；链接迁移代码与验证 | 实现时设计；交付前验证 |
| 新增可运行能力或变更安装/使用流程 | 更新指南：环境、依赖、命令、预期输出、退出/清理与排障 | 能力交付时 |
| 依赖升级或新增平台/客户端支持 | 记录选择或升级原因、精确版本、平台及兼容验证；重要替换补 ADR | 同步交付 |
| 修复用户可见问题、数据一致性问题或安全缺陷 | 记录触发条件、实际影响、修复后的行为和回归证据；纠正相关指南/参考；重要变化进入未发布记录 | 同步交付 |
| 执行技术验证、故障测试或阶段验收 | 写明实际环境、版本、步骤、结果、限制和证据；更新进度及仍未通过项 | 结果产生后、宣告完成前 |
| 阶段完成 | 逐项核对出口条件，汇总证据、遗留问题和下一阶段依赖 | 阶段标记完成前 |
| 发布、废弃或不兼容变更 | 更新变更记录、发布说明、兼容边界、升级/迁移/回退方法；明确不支持回退的情况 | 发布前 |
| 删除、重命名或移动功能/文档 | 删除失效使用说明或标记废弃；更新所有受影响的相对链接和索引 | 同步交付 |

仅格式调整、拼写修正或不改变行为和维护方式的内部小重构，可不新建开发文档；交付说明注明“不涉及开发文档更新”及具体理由。只修正文档错别字时，不要求更新所有日期、进度和变更记录。每个函数不必配一份文档，每个提交不必新增一条 ADR。

## 4. 各阶段的最小文档门槛

这是沿用总体规划 P0–P5 的开发门槛，不是增加产品范围。每阶段只补当时需要的内容；文档存在不等于阶段通过。

| 阶段 | 阶段完成前需要具备的文档 |
| --- | --- |
| P0 技术与契约 | 环境/依赖及外部客户端验证；关键技术决策；请求/结果、状态转换与 Node 协议契约；明确未验证边界 |
| P1 单节点链路 | 当前架构与模块职责；配置/身份和 fs.list 接口；启动/接入指南；持久化与幂等说明；单节点实际链路证据 |
| P2 受控进程 | 授权/审批规则、启动 journal、进程生命周期、取消/超时/输出限制；对应 CLI 指南与真实进程验证 |
| P3 双节点路由 | placement 规则、资源/版本证据、槽位语义；双节点配置与正负例验收 |
| P4 故障闭环 | 故障矩阵、重启/对账/未知状态处置、存储失败行为；故障注入证据及排障指南 |
| P5 发布 | fs.read/产物/留存参考；安装、迁移、备份恢复指南；A01–A16 验收与客户端支持范围；变更记录和发布说明 |

例如，当前 P0 探针通过只能记录 stdio 接入验证；不能将其写成 Server–Node 链路、进程执行或 A02 全部通过。

## 5. 写作与证据标准

每份实质性开发文档应包含：用途和范围、状态、适用阶段/软件或协议版本、更新日期、维护责任，以及相关代码/决策/验证链接。可用一行或小表格表达，不要求逐页套用繁重封面。维护责任写真实负责人或“当前工作项开发者/项目维护者”，不得虚构审核人。

文档状态建议使用“草案、现行、已替代、已归档”；决策使用“提议、已接受、已拒绝、已替代”。功能状态使用“未开始、进行中、待验证、已完成、受阻”。“已完成”要求对应验收与文档门槛都满足，不能单凭代码写完或日期到达标记。

写作要求：

1. 先写结论、行为或操作目标，再解释细节。教程、操作指南、技术参考和设计解释可以分开，也可以在小文档中用明确章节分开，避免读者找一个命令却必须读完整设计讨论。
2. 使用项目统一术语。Task/会话与 execution 分清；Node 断线、UNKNOWN、取消请求和已取消不得混用；MCP 协议版本、Node 协议版本、数据库 schema 版本和软件版本分别标明。
3. 示例注明操作系统、shell、工作目录、环境前提和副作用。保留字段的真实拼写；示例值和占位符明确标识。示例无法实测时注明未验证，不编造输出。
4. 验证记录至少包括日期、工作项/验收编号、代码 revision（未提交时写基础 revision 与工作区差异）、工具/依赖/客户端版本、步骤或测试命令、实际结果、未覆盖项和证据位置。精简原始输出，只保留支持结论的内容并脱敏。
5. “历史记录转述”“本次复验”“目标要求”明确分开。只有构建成功不能声称运行支持；一个 WSL 环境不能代替两个真实 Node；SDK 自测不能代替外部客户端调用。
6. 链接使用仓库相对路径，优先引用已存在的权威页面和版本化代码。涉及外部标准/SDK 行为时引用官方来源及实际使用版本；不要用搜索结果摘要当最终依据。
7. 不保存 token、密码、真实敏感数据或完整私人会话。必要示例使用脱敏数据。图与正文同步修改，图不能代替接口定义或验收证据。

## 6. 文档演进与最小模板

普通文档使用稳定主题名，如 `参考/MCP工具.md`，以 Git 保存修订历史，不每次复制 `v2/最终版/最新版`。只有需要同时维护不兼容的已发布版本时才分版本，说明适用范围和入口。ADR 使用连续编号，如 `决策/0001-决策主题.md`；验证记录可用 `验证/2026-09-10-P0-验证主题.md`。

无需提前生成模板文件。按需要使用以下最小结构：

| 类型 | 必需内容 |
| --- | --- |
| 设计说明 | 问题与目标、范围与约束、当前/目标设计、关键流程和失败行为、接口影响、验证方法、未决项 |
| ADR | 编号与标题、日期与状态、背景、备选方案、决定与理由、代价和后果、关联实现/验证、替代关系 |
| 接口参考 | 用途、输入/输出、必填/默认/限额、权限、状态/错误、幂等/取消等适用语义、示例、兼容性 |
| 操作指南 | 目标、前提、步骤、预期结果、验证、失败处理、必要清理/回退 |
| 验证记录 | 验证对象与版本、环境、场景及命令、期望与实际结果、证据、限制和后续动作 |
| 阶段进度 | 工作项、状态、完成依据、剩余条件、依赖/阻碍、下一步 |

已接受的 ADR 不覆盖原决定来掩盖历史：新决定以新 ADR 替代，旧页更新状态并互链。事实性勘误可直接修正并注明原因。废弃文档保留说明和替代链接，不能让旧入口继续指导错误操作。

发布变更记录位于 `docs/发布/变更记录.md`，出现首个需要面向使用者记录的变更时创建。先进入“未发布”，发布后按版本和日期归档；使用“新增、变更、废弃、移除、修复、安全”等分类，仅保留有内容的分类。不要直接复制 git log，也不要为日常编辑行为制造发布条目。

## 7. 工作项完成检查

交付前由本次开发者核对以下事项；使用 PR 时在描述中列出更新的文档或不适用理由，不另建重复的逐提交检查档案。

- [ ] 已对照触发表检查本次变更；需要的设计/ADR 已记录。
- [ ] 代码、配置、接口、示例和操作指南一致；未实现能力未写成可用。
- [ ] 已记录适当的实际验证和限制；必要文档缺失时未标完成。
- [ ] 当前工作项/阶段状态已更新；局部通过未扩大为完整验收。
- [ ] 新开发文档位于 `docs/`，正文简体中文；新增入口已加入相关索引。
- [ ] 相对链接、代码路径、命令前提和必要脱敏已检查。
- [ ] 重要兼容性/使用行为变化已进入适当的未发布记录或迁移说明。

此规则先由开发者和编码代理执行，不声称已经有 CI 自动强制检查。后续有稳定文档工具链时，可加入 Markdown/链接检查；命令和业务结论是否正确仍需实际验证与评审。无法补全验收时，记录缺口并保持“待验证/受阻”，正常开发范围内的文档维护无需额外批准。

## 8. 实践依据

本规范借鉴以下公开实践，并按单人维护、Go/MCP 执行后端的规模裁剪；本项目的简体中文、目录和阶段门槛来自用户要求与既有规划。

- [Diátaxis](https://www.diataxis.fr/start-here/)：按教程、操作指南、参考和解释组织信息；[实施建议](https://www.diataxis.fr/how-to-use-diataxis/)强调按需求应用，不创建空结构。
- [AWS ADR 指南](https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/introduction.html)：保存重要决定的背景、理由与取舍，支持后续维护和交接。
- [Keep a Changelog](https://keepachangelog.com/en/1.1.0/)：维护面向人的重要变更记录，区分未发布和已发布内容，避免把提交日志当发布说明。
