# RunWeave v0.0.1 可执行性、维护性与扩展性审计

日期：2026-09-09。性质：设计审计，不是代码审计；仓库尚无实现，本文不声称系统已经通过验证。

审计主体：[RunWeave-v0.0.2-项目规划书.md](./RunWeave-v0.0.2-项目规划书.md)。旧版半年计划仅用于了解 Go、单人开发的背景，不作为新版本范围依据。

用户已确认：**v0.0.1 先做 MCP 执行层；沿用 Go；Linux 执行节点优先。** 其余技术细节是本次审计形成的建议，实施方案见 [v0.0.1 实施规划](./RunWeave-v0.0.1-实施规划.md)。原规划保留为产品愿景，不直接修改。

## 1. 审计结论

**方向可落地，单体架构选择合理；但原规划还不能直接充当 v0.0.1 的开发规格。** 缺口主要在执行语义和范围约束，而非缺少组件。若照章节逐项实现，很容易先写完 Agent、Registry、EventBus，最后才发现跨节点状态、安全和客户端交互需要重做。

建议将首版定义为：一个可信所有者管理两台 Linux Node，第三方 Agent 通过 MCP 提交明确操作，RunWeave 根据能力与资源位置选择节点，经过节点授权后执行，并提供可查询、可取消、可解释的结果。

| 维度 | 判断 | 达到可开工状态所需调整 |
| --- | --- | --- |
| 技术可执行性 | 核心链路可实现；原版完整范围偏大 | MCP 前置，删除首版自有推理循环；补齐断线、重复派发和审批语义 |
| 维护性 | 单进程 Server、Go、SQLite 是合适起点 | 单一执行入口和状态写入路径；避免九个概念变成九套框架 |
| 扩展性 | Execution、Resource、Protocol 边界有价值 | 协议版本、资源版本、身份与授权上下文现在定义；扩展实现按需增加 |
| 安全承诺 | 原表述超出所列机制能保证的范围 | 明确可信执行环境；文件 API 边界不等于进程沙箱；输出也可能泄露数据 |
| 产品验证 | MCP 是可验证的入口 | 一个真实客户端闭环优先；不预设自动调用、零获客成本或企业采购成立 |

这是一份条件性可行结论，不是工期或市场成功保证。关键未知应由实施规划中的里程碑验证，不能靠继续增加抽象解决。

## 2. 应保留的设计

1. **控制平面与执行平面分离，但 Server 保持单体。** 网络边界确实存在，没必要在 Server 内再制造网络边界。
2. **Capability 与 Resource 分开。** 有 Python 不代表拥有数据；有数据不代表运行环境可用。
3. **Node 主动连接 Server。** 适合本地与内网节点，减少入站端口配置；实际连通性仍取决于代理、防火墙和证书环境。
4. **确定性 placement。** 先证明“为什么选这台、为什么没有可选节点”，不引入模型打分和权重调参。
5. **Execution 是独立记录。** 连接、调用方会话与具体远程操作不能混为一个生命周期。
6. **Node 有最终否决权。** Server 的路由和权限检查不能代替 Node 本地策略。
7. **结果摘要与原始输出分离。** 有界结果、产物引用和持久状态有助于长期维护。
8. **暂不做微服务、DAG、自动迁移、企业权限平台。** 这些暂缓不会妨碍验证核心价值。

## 3. 必须先修正的可执行性缺口

P0 表示在依赖它的实现开始前必须明确；P1 表示首版发布前必须处理。严重度针对本次首版，不代表所有功能都应立即实现。

### F01 / P0：自然语言任务和执行操作之间缺少责任归属

**依据：** 原文 §5.1、§6.2。MCP 示例只传 `requirements` 和自然语言 `task`，没有具体程序、参数或文件操作。

例如“训练 SAR 模型”无法被确定性执行层直接执行。若 Server 将它转换成脚本，就已经在实现一个 Agent；若 Node 转换，则提前引入 Edge Agent。

**处理：** 第三方 Harness 负责推理和操作构造，RunWeave 接收有 schema 的 `operation`。首版支持 `fs.list`、`fs.read`、`process.exec`；自然语言说明仅供审计展示。不保证 RunWeave 自动推断模型、训练命令或依赖安装方式。

**验收：** 不提供 LLM API Key，仍能经 CLI 和 MCP 跑通相同请求；缺失操作字段时直接报参数错误。

### F02 / P0：目录限制和命令名称分类无法构成 shell 安全边界

**依据：** 原文 §5.7、§9.2 将 `pytest` 设为 ALLOW，把 `sudo` 设为 DENY，并以 roots 和工作目录描述 shell 安全。

`pytest` 会执行仓库代码；Python、构建脚本和 Git hooks 也能执行任意逻辑。指定 cwd 不会限制子进程访问其他目录或网络。禁用某个命令名也不能阻止同权限代码完成同一操作。

**处理：** `process.exec` 被定义为受信任环境中的代码执行，默认 ASK；执行前由 Node 所有者批准。只提供程序标识与 argv，不默认经过 shell。用户可为自有可信项目显式设置 ALLOW，但产品不能把它宣传成安全分类器。首版不支持不可信代码强隔离、生产敏感环境或恶意本地同权限用户。

文件 API 单独使用基于目录句柄的访问边界，并测试符号链接和路径穿越；先解析路径再检查前缀不足以解决竞态。[Go 文件访问设计说明](https://go.dev/blog/osroot)

**验收：** 文件越界被拒；进程能力默认需授权；文档明确进程权限等于运行账号权限。若目标用户要求运行恶意代码，则必须先调整范围加入真实隔离，不能仅调整文案。

### F03 / P0：断线不代表远程操作已经失败或停止

**依据：** 原文 §10.1 把 `NODE_LOST` 作为异常态，但没有明确是否终止、重试或恢复。

危险场景：Node 已执行写入，结果发送前断线；Server 将其标为失败并换节点重试，产生重复副作用。另一个场景是 Server 重启后把原来占用的 Node 当成空闲节点。

**处理：** 区分“执行结果未知”和“执行失败”。保留 `UNKNOWN`；重连只查询和对账，不自动重跑。Server 持久化幂等键与派发意图，Node 持久化 execution 接收记录和结果；相同 execution 不再次启动。未知状态未核实前不释放相应执行槽。

**验收：** 丢失启动确认、丢失结果、Server 重启、Node 重启时均不自动重复副作用；无法证明未执行时诚实返回未知。这里不承诺 exactly-once。

### F04 / P0：跨节点修改和验证，与“不自动迁移文件”存在缺口

**依据：** 原文 §5.4 将一个仓库列为多位置；§12.1 Demo 3、§12.2 Story D 要在 A 改代码、B 验证；§15 不自动迁移文件。

`repo://x` 在两台机器上存在，不代表内容相同。即使 commit 相同，未提交文件、子模块、LFS 内容和运行依赖也可能不同。单纯调度到 B 不能使 A 的修改出现在 B。

**处理：** URI 表达逻辑身份，具体位置包含版本证据。跨节点复现必须请求显式 revision，Node 在执行前复核。首版演示独立资源上的连续操作，或操作者事先准备好的同版本干净工作树；不演示系统尚未实现的透明代码同步。

**验收：** 相同 URI、不同 revision 不会静默替代；要求可复现代码时，脏工作树被拒；不满足资源共址条件时明确失败。

### F05 / P0：MCP 长任务不能只按同步函数包装

**依据：** 原文 §6.2 直接返回 `ExecutionResult`，但 §10.1 和 Demo 包含训练、下载、等待审批。

一次 MCP 请求、远程执行、调用方会话是三个不同生命周期。依赖客户端一直等待会导致超时、重连丢状态及重复提交。标准能力支持还取决于具体客户端。

**处理：** 首版采用普通 MCP 工具 `execute / get_execution / cancel_execution`：提交后快速返回持久 execution ID，再查询结果。原始 tool-call 取消不等于撤销已经提交的远程执行；需要显式取消工具。MCP Tasks 扩展作为以后适配项，不作为首版依赖。[MCP Tasks 官方说明](https://modelcontextprotocol.io/extensions/tasks/overview)

MCP schema 使用正式字段 `inputSchema`；结果通过 `structuredContent` 返回并附精简文本兼容表示。工具声明不替代授权。[MCP Tools 规范](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)

**验收：** 真实客户端能完成提交、查询、审批等待提示和取消；客户端退出后仍可用 CLI 找回 execution。不能把“协议连通”当成“Agent 会稳定使用”。

### F06 / P0：审批必须绑定具体操作，不能成为通用放行开关

**依据：** 原文 §5.7、§9.1、§9.5 分别提出审批、Node 最终授权和简单 token，但尚未定义关联关系。

审批以后参数改变、资源映射改变、Node 重连或换节点，原审批是否有效？如果这些没有约束，后续界面和协议都容易返工。

**处理：** 首版采用 Node 本地 CLI 审批，绑定 execution ID、Node、请求摘要、资源映射与策略版本、有效期。重放不能启动第二次；内容变更必须重新提交。MCP 不暴露审批工具。节点凭据与调用方凭据分离，凭据不直接由请求中的 `node_id` 决定身份。

**验收：** DENY 无法被审批覆盖；过期审批、其他 Node 的审批、参数被改的审批均无效；简单凭据也支持撤销。

## 4. 发布前需收紧的设计

| 编号 | 原文位置与问题 | 首版处理 |
| --- | --- | --- |
| F07 / P1 | §5.5 混合硬性能力、资源与排序偏好；heartbeat 最新不能证明延迟最低 | 所有必需能力和资源必须同时满足；在线、空闲是准入条件；合法候选按用户偏好、node_id 排序，心跳只用于存活判断 |
| F08 / P1 | §10.3 内存 EventBus 被赋予审计、重放等职责 | 状态和持久事件同一事务提交；通知可丢失，事实不能丢；首版不做 EventBus 框架或事件溯源 |
| F09 / P1 | §5.6 默认能得到完整 mutation 和语义摘要 | 返回退出码、截断信息、产物引用；进程 mutation 默认 unknown，限定范围的 Git 差异仅是 best-effort；不伪装成完整审计 |
| F10 / P1 | §9.3 数据不搬运被延伸为数据不外泄 | 源数据不自动同步，但 stdout、读文件结果、指标、产物都可能包含原数据；逐类输出授权，默认日志留在 Node |
| F11 / P1 | §13 先实现 Agent Kernel，MCP 到最后才验收 | 第一条纵向链路即通过 MCP；CLI 是诊断入口；资源、授权、故障语义与执行同步建立 |
| F12 / P1 | 文件名 v0.0.2、正文 v0.1、用户首发 v0.0.1 混用 | 文档修订号不等于软件版本；新实施规划是首发范围依据；旧半年路线不直接排期 |
| F13 / P1 | §10.1 保留 process handle，但未说明子进程 | Linux 进程组终止与回收必须实测；不支持自行 daemonize/脱离进程组的作业；Windows 后续单独验收 |

Go 的 `CommandContext` 默认取消机制不能自动表达 RunWeave 所需的整个作业生命周期；需要明确进程组和管道回收策略。[Go os/exec 文档](https://pkg.go.dev/os/exec)

## 5. 维护性：建议采用的最小结构

**一个仓库、一个 Go module、一个二进制的多个子命令；一个 Server 进程、每台设备一个 Node 进程。** MCP stdio bridge 是调用方启动的薄代理进程，不另存执行状态。

边界按变化原因划分：

| 边界 | 独立原因 | 不应承担的职责 |
| --- | --- | --- |
| 协议与请求/结果类型 | 两端升级和跨进程通信 | 调度、数据库、MCP 会话状态 |
| Server 执行服务 | 提交、placement、状态转换需要一致性 | 进程启动和本地物理路径解析 |
| Node | 最终授权、资源解析、进程与文件操作 | 自主推理、跨节点调度 |
| SQLite 存储 | 事务、迁移与查询有自己的变化节奏 | 以通用 ORM 或 Repository 框架重建领域 |
| MCP / HTTP / CLI 适配 | 接入协议各异但用例一致 | 各自复制 placement、取消、幂等逻辑 |

不为 Agent、Task、Placement、Policy 九个名词逐个设计接口层。Placement 首版是纯函数；Policy 是明确规则和结果类型；Task 先保留可选关联 ID。优先使用具体 Go 类型，只有进程控制、节点通信等真实边界需要小接口。

**首版必须留下的维护资产：** 请求与结果示例、协议兼容策略、状态转换表、数据库迁移、故障测试、配置示例和排障文档。它们比空的插件目录更有价值。

## 6. 扩展性：保留边界，不预付实现成本

| 未来变化 | 首版保留什么 | 何时才实施 |
| --- | --- | --- |
| 自有 Harness | 独立于 MCP 的执行服务与 correlation_id | 执行层已有使用反馈，确有自有交互需求 |
| Windows Node | 进程控制放在平台文件；协议无物理路径依赖 | Windows 进程树、路径及服务生命周期验收完成 |
| 新工具/沙箱 Node | 有版本的 operation 与显式 capability | 出现第二种真实执行器，而非为了插件化而插件化 |
| PostgreSQL | SQL 聚合在存储包，事务边界清楚 | 单机写入能力或部署需求经测量不足；迁移并非换连接串即可 |
| 多 Server | 稳定 execution 身份、节点 fencing 与故障语义 | 真正需要 HA；届时补分布式租约和一致性，不预先引入消息队列 |
| 产物对象存储 | 不透明 artifact ID、元数据与授权读取接口 | 本地留存和传输成本成为实际瓶颈 |
| 工作流与恢复 | Execution 独立记录，未知结果可表示 | 有依赖关系、幂等补偿和重试策略的真实需求 |
| 团队权限 | principal_id 与 Node 所属关系来自认证 | 存在多个互不信任主体；新增 RBAC 不能只靠补一列 owner_id |

Windows 的进程树管理有平台专属机制，应作为单独功能验证，不因 Go 能交叉编译就宣称支持。[Windows Job Objects 官方文档](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)

## 7. 产品叙事与验证边界

原文 §2.2 的“获取成本几乎为零”、§6.4 的“MCP 主要只是包装”、§16.1 关于其他调度器只能处理预定义任务的论述，均不应作为已经验证的结论。

本次不做完整竞品或市场调研。更稳妥的价值主张是：**让已有 Agent 使用用户管理的多台机器，在能力与资源约束下执行，并提供节点授权、结果查询及可解释的路由。** 差异是否足够，应让试用者比较“RunWeave”和他们当前的 SSH、脚本或已有调度工具所需的实际工作量。

首版只声称支持经过测试的一个具体 MCP 客户端版本。工具被注册不意味着模型每次都会正确选用；把发现能力、构造 request 和轮询说明作为接入体验的一部分验收。

隐私承诺应改为“原始资源不被自动复制到控制平面；返回内容遵守配置的输出策略”。任意代码执行与强保密不能同时仅靠几条命令规则实现。

## 8. 可开工条件

本次已确定 MCP 优先、Go、Linux Node；配套实施规划给出了其余默认方案。因此无需继续等待大而全的架构设计，也无需再研究另一套框架。

在实际开始编码时，先冻结最小请求样例、幂等/断线语义、默认授权模式和第一个验收场景，再做一条可运行的纵向链路。若第一阶段的客户端、进程回收或依赖打包验证失败，调整对应设计，不扩大首版范围掩盖问题。

本文不授权或启动实现；此次交付到方案规划为止。
