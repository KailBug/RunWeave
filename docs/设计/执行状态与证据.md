# 执行状态与证据

状态：现行，纯契约实现与验证已完成。日期：2026-09-11。适用范围：P0-03 / v0.0.1。维护责任：当前工作项开发者。

依据：[ADR 0003](../决策/0003-执行证据与Node协议.md)。本页是状态、取消、占槽与证据的权威定义；消息字段见[Node 协议](../参考/Node协议.md)。本阶段实现纯转换，不提供 daemon 或持久执行。

## 状态与占槽

| 状态 | 事实与合法后续 | 占槽 |
| --- | --- | --- |
| CREATED | Server 已持久化，尚无派发意图；可 DISPATCHING、本地 REJECTED/CANCELLED | 否 |
| DISPATCHING | 已占槽且可能到达 Node；可 WAITING_APPROVAL/RUNNING/可信终态/UNKNOWN | 是 |
| WAITING_APPROVAL | Node 已接收，等待审批，未确认启动；可 RUNNING/拒绝/取消/审批过期/UNKNOWN | 是 |
| RUNNING | 启动已确认；可 SUCCEEDED/FAILED/CANCELLED/TIMED_OUT/UNKNOWN | 是 |
| UNKNOWN | 执行或清理事实不足；必须凭当前 Node journal 证据恢复，不能改选节点重跑 | 是 |
| SUCCEEDED/FAILED/REJECTED/CANCELLED/TIMED_OUT/EXPIRED | 可信终态；永不被自动改写 | 否 |

派发前在同事务内复查合法候选、占用唯一槽位和写入派发意图；发送只能发生在事务提交后。批准等待与 UNKNOWN 均不允许超发。启动事实为 not_started / started / uncertain；已知 started 不允许恢复为未启动。

## Node journal 与顺序

每个 execution 的 revision 为持久单调正整数（上限 JSON 安全整数），阶段为 RECEIVED、WAITING_APPROVAL、START_COMMITTED、RUNNING、UNRESOLVED、FINISHED。同一事实重发保持 revision 和内容；新的事实先持久化再提高 revision。START_COMMITTED 表示启动已承诺但实际开始未确定，对 Server 映射 UNKNOWN。确认已开始才报告 RUNNING。审批信息随 WAITING_APPROVAL 一起持久保存。

UNRESOLVED 用于 Node 重启后无法核实工作或清理的情况，必须带 start=started 或 uncertain，对 Server 映射 UNKNOWN。已知 started 不得改为 uncertain；journal 原 RUNNING 不足以在新 daemon 中继续声称受管理运行。UNRESOLVED 可凭新证据恢复 RUNNING 或已知终态，不回退 RECEIVED/WAITING_APPROVAL。它与 START_COMMITTED 的模糊启动窗口都禁止自动重跑。

Server 记录最近 revision、阶段、证据摘要、启动事实和终态结果摘要。低 revision 迟到消息忽略；同 revision 不同内容产生冲突，不能更新状态或发成功 receipt。状态回退也产生冲突。可信 FINISHED 可以从 DISPATCHING/WAITING_APPROVAL 直接到终态，不能因中间通知丢失拒绝事实。

重连 snapshot 必须匹配尚在等待的 query message_id、execution、请求摘要、当前 Node 和 epoch；这些来自 Server 保存的请求上下文。相同 revision 的当前 snapshot 可将断线造成的 UNKNOWN 恢复为原已知阶段；未经查询确认的重复通知不能这样恢复。ABSENT 快照不证明从未执行，UNKNOWN 与槽位保持不变，不能再派发或返回 CANCELLED。

## 终态证据

Outcome 包含 `{state,start,quiescent,result}`。quiescent 必须 true，表示无未清理的受管理工作；声明 false 的报告不足以构成终态，应保留 UNKNOWN。Result 使用[P0-02 定义](../参考/业务请求与结果.md)。

| state | 要求 |
| --- | --- |
| SUCCEEDED | start=started，Result 无 error |
| REJECTED | start=not_started，错误为 POLICY_DENIED/APPROVAL_DENIED/RESOURCE_UNAVAILABLE/REVISION_MISMATCH/PROGRAM_UNAVAILABLE/PATH_DENIED |
| EXPIRED | start=not_started，错误 APPROVAL_EXPIRED |
| CANCELLED | start 为 not_started 或 started，错误 CANCELLED；不能由 cancel_requested 单独推导 |
| TIMED_OUT | start=started，错误 TIMED_OUT |
| FAILED | error 为其他执行失败码；未启动时仅 PROCESS_START_FAILED，必须确认失败而非模糊窗口 |

未启动 Outcome 不得携带文件正文、产物、已产生进程输出或退出码。已知 START_COMMITTED 之后不能恢复 RECEIVED/WAITING_APPROVAL；允许确证 PROCESS_START_FAILED，不允许凭空报告未启动拒绝。收到与已确认 started 相矛盾的未启动 Outcome 必须保留原事实并记冲突。

结果摘要为 SHA-256(`runweave-outcome-v1\n` + 规范 Outcome JSON)，外部表示 `sha256:<小写hex>`。Result 默认值按 P0-02 补齐；数组顺序保留。重发必须复用持久结果及其顺序，不重新生成时间/产物/目录顺序。相同已知终态和摘要为重复；不同终态或内容为冲突，永不覆盖已知终态。

Server 只有在状态、结果、槽位释放与事件已提交后才能发送 result.receipt，receipt 同时绑定 execution、请求摘要、Outcome 摘要。Node 收到一致 receipt 才能标记结果已确认；丢 receipt 时补报同一结果。纯函数返回成功不代表事务已提交。

## 取消与竞争

cancel_requested 独立且只增不减。非终态收到取消先持久保存意图，再尽力通知 Node；重复取消幂等。终态后取消不重写结果或补造取消事实。CREATED 可在取消意图持久化后本地完成 CANCELLED；已经可能派发的执行必须等待 Node 未启动取消或已停止回收证据。

自然完成与取消竞争时按真实证据保留 SUCCEEDED/FAILED，cancel_requested 仍可为 true。离线取消保持 UNKNOWN，不伪报 CANCELLED。Node 重连先应用待处理取消/对账，再开放槽位；本地运行 deadline 不依赖连接存活。审批 TTL 不消耗运行 timeout，过期与启动必须在 Node 启动前事务/复核中裁决。

## 失败与后续证据要求

| 场景 | 生产实现必须证明 |
| --- | --- |
| 接收确认丢失、重复 dispatch | 同 ID 同请求摘要重报 journal，不二次启动；异摘要拒绝 |
| START_COMMITTED 后崩溃 | 不盲目重跑；残留进程与管道未确认时 UNKNOWN 并隔离 Node |
| Server 重启/旧 epoch | 从持久槽位恢复，旧连接无权更新；新连接完成查询对账 |
| result/receipt 丢失 | 重传原结果；只在 Server 事务成功后确认 |
| journal/事件/磁盘失败 | 不能保存启动事实则不启动；不凭内存释放槽位或返回成功 |
| snapshot 缺记录或永久失联 | 保持 UNKNOWN；重装撤销旧身份，不将新空库当作旧工作已清理 |
| 取消、超时和完成并发 | 有真实后代退出/管道回收证据；副作用计数器证明无重复启动 |
