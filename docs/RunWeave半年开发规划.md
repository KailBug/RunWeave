## 1. 半年目标

半年结束时，RunWeave 应允许一个真实的外部 MCP 客户端发现两个 Linux Node，根据明确的能力和资源要求提交操作，在 Node 授权后执行，并查询结果、请求取消、处理离线与恢复。

同时，一名没有参与实现的使用者应能依据文档完成安装、配置、运行 Demo 和基本排障；维护者应能升级、迁移、备份恢复并定位一次失败执行。完成这些能力比增加工具数量更重要。

| 半年成果 | 要证明的事实 |
| --- | --- |
| 可运行首版 | v0.0.1 全部核心范围形成端到端闭环 |
| 真实路由 | 两 Node 不同资源/能力，合法选择与拒绝均可解释 |
| 可靠执行语义 | 重复提交不重复启动，未知不自动重跑，取消不伪装成已停止 |
| 节点控制权 | 身份绑定、本地审批和输出授权可验证 |
| 安装与接入可用 | 一个明确版本的真实 MCP 客户端完成完整交互 |
| 维护可持续 | 测试、迁移、恢复、日志与发布流程可交接 |
| 产品判断有证据 | 记录试用者的配置负担、重复使用和失败原因，决定下一阶段 |

### 1.1 计划不自动扩张的软件范围

v0.0.1 范围沿用实施规划：Server、Node、CLI、MCP；fs.list / fs.read / process.exec；手工资源；确定性 placement；一 Node 一槽；幂等、审批、取消、超时、UNKNOWN、对账、输出及产物限额。

六个月内不自动安排自有 Agent Loop、Web Dashboard、原生手机 App、DAG、自动重试、文件同步、Windows 原生 Node、强沙箱、插件平台、多租户或多 Server。任何新增方向先有使用证据与独立范围决策，不作为半年完成的必要条件。

## 2. 时间与工作量假设

实施规划将 P0–P5 估为 **31–46 有效人日**，按每周五个有效开发日、另加 25%–35% 联调缓冲，约为 **8–13 周**。这是首版估算，不是半年总工时，也不是已经验证的生产率。

本计划以第 13 周作为首版发布检查点，将后续 13 周用于产品试用与维护。每个月按工作周划分，因此不与自然月逐日对应；实际起止日期在开工后填写，不默认今天就是开工日。

假设开发者熟悉 Go，拥有两台可测试 Linux 环境和一个可用 MCP 客户端。若每周有效投入较少，应按实际人日重排。第 1 周技术验证完成后第一次重估；此后每月底根据已完成验收更新预测。

后半程工作量由实际问题决定，不提前填满新增功能。未使用的缓冲用于复现、文档、恢复演练和必要维护，也可以提前完成计划。

## 3. 技术基线与开发规则

### 3.1 保持简单的架构

一个仓库、一个 Go module、一个二进制；Server 单进程，Node 每台设备一个 daemon，MCP stdio bridge 为无执行状态的薄代理。Server API 是 MCP 和 CLI 的共同执行入口。

使用本机 SQLite 保存事实与事件，Node 保存接收 journal、审批和结果；输出文件留在 Node。WebSocket 承担 Server–Node 通信；不引入独立消息队列、微服务或事件溯源。

具体工具链、官方 MCP Go SDK、SQLite 驱动和 WebSocket 库在 P0 锁定。版本兼容、schema 迁移和配置限制进入仓库文档，不依赖维护者记忆。

### 3.2 先完成可运行链路

每个阶段从输入到结果形成可验证增量。不得先花一个月搭 Agent 框架、通用接口和空模块，再验证 MCP 与 Node 能否真正协作。

第一条链路包含认证、明确资源、持久请求和幂等键；第一次进程执行就包含默认 ASK、启动 journal 和取消/超时。后续阶段扩展故障覆盖，而不是首次加入这些基本语义。

### 3.3 不可裁剪的底线

1. 外部 Harness 构造明确 operation，RunWeave 不隐式解释自然语言。
2. Node 最终授权；MCP 不提供自我批准工具。
3. 重复消息不能重复启动；模糊结果报告 UNKNOWN，不能自动重跑。
4. 未解决 UNKNOWN 和审批等待占用执行槽。
5. 资源版本不符不能静默替代；不隐式同步代码。
6. 进程超时、取消、输出排空和子进程回收必须验证。
7. 状态、事件和防重记录持久化；磁盘不可写时不能照常启动。
8. 文件访问边界不宣称是进程沙箱，数据局部性不宣称是零外泄。

## 5. 第 1 月：契约、技术验证与 MCP 单节点闭环

### 5.1 目标

外部 MCP 客户端不依赖 RunWeave 的 LLM Key，即可发现授权资源、提交 fs.list，并通过 execution_id 查询结果。认证和持久执行记录从第一条链路就存在。

### 5.2 每周任务

| 周 | 工作包 | 可检查产出 |
| --- | --- | --- |
| W01 | P0：锁定依赖；真实客户端连接 SDK 最小示例；验证 Linux 进程组终止；冻结 Request/Result、幂等与 UNKNOWN | 依赖版本清单、客户端记录、进程回收实验结果、契约 fixture、简短决策记录 |
| W02 | P1：Server/Node 命令、认证、手工资源、注册心跳、协议版本、SQLite 迁移、状态目录独占锁 | 启动两个角色；错误身份被拒；第二个 daemon 不能占用同目录 |
| W03 | P1：fs.list、持久提交/查询、稳定 request_id、MCP stdio bridge 与 CLI API 接入 | 真客户端看到远程目录列表；同键重试返回同 execution；重开 CLI 可查询 |
| W04 | 完成 P1 负例；P2 起步：程序映射、Node journal、本地审批记录与请求摘要 | 参数/资源错误不执行；进程请求默认进入等待审批，尚未批准不启动 |

### 5.3 本月模块范围

按实际代码创建 cmd、contract、protocol、server、node、store、api、mcp。先用具体类型与小函数；Server 状态路径统一，MCP 不直接读写执行表。目录拆分随实现出现，不预建 Agent、TaskGraph、插件接口。

### 5.4 月底验收

真实 MCP 客户端及版本已记录；单节点 fs.list 完整闭环可重复运行；请求退出会话后仍可查；基础身份和文件根目录约束可验证；幂等冲突报错；日志不污染 MCP stdout。

**不算完成的情况：** 只有 Server 能看到 Node 在线，或只有 SDK 自带示例能运行，而 RunWeave 的端到端链路仍未接通。

若 SDK、驱动或进程回收验证失败，本月先调整对应依赖/平台实现；不通过新增 Agent 层绕开问题。

## 6. 第 2 月：受控执行与双节点调度

### 6.1 目标

Node 批准后执行真实前台进程，支持本地超时与显式取消；两台真实 Node 按能力、资源、版本和执行槽进行选择。

### 6.2 每周任务

| 周 | 工作包 | 可检查产出 |
| --- | --- | --- |
| W05 | P2：完成 process.exec、program/argv/cwd 解析、本地 approve/deny、审批过期和变更失效 | 已批请求执行；错误 Node、改参数、改策略和过期审批均不能放行 |
| W06 | P2：进程组、终止宽限期、强制回收、stdout/stderr 有限落盘；完成/取消竞争 | 真实测试子进程退出；大输出持续排空；cancel_requested 与已取消分开 |
| W07 | P3：两 Node、资源位置/revision、能力过滤、偏好排序、事务占槽、placement trace | 不指定节点也能选中正确位置；忙、无共址、版本错有明确负例 |
| W08 | P3 收口、P4 起步：掉线注入、丢确认、重复派发、本地结果补报与 receipt | 副作用计数器不重复启动；UNKNOWN 不释放执行槽；初步故障矩阵 |

### 6.3 本月必须明确的语义

一次 execution 的所有资源必须在同一个 Node 上满足。Heartbeat 只表示在线，不能代表最低延迟。每 Node 一槽包括等待审批与未知执行，没有等待队列。

程序由 Node 本地映射，argv 不默认交给 shell，环境中不继承连接 token。pytest、解释器和构建脚本都按代码执行授权，不建立“命令名看起来安全即可自动执行”的规则。

同一 URI 的两份仓库分别记录 revision。要求固定版本时检查实际状态；不为 Demo 临时加入隐式 git pull、scp 或同步功能。

### 6.4 月底验收

真实受管理作业可运行、取消和超时；ASK/ALLOW/DENY 有明确边界；双节点路由和拒绝原因正确；并发请求不超发；重复消息不会重新启动相同 execution。

本月可以完成内部 Demo，但不能据此对外宣称首版已可靠：完整重启对账、产物授权、安装恢复尚待第 3 月收口。

### 7.1 目标

完成 P4/P5，让“执行成功、明确失败、结果未知”都能被系统诚实表达；通过 A01–A16 后发布 v0.0.1。

### 7.2 每周任务

| 周 | 工作包 | 可检查产出 |
| --- | --- | --- |
| W09 | P4：Server 重启、Node 重连、epoch 校验、状态/事件事务与结果 receipt | 旧会话被拒；重启后先对账；丢结果可补报且无重复副作用 |
| W10 | P4：Node 崩溃窗口、残留进程、离线取消、磁盘故障、终态竞争 | 不能证明未启动时报 UNKNOWN；残留未核实则不可调度；磁盘失败不启动 |
| W11 | P5：fs.read、artifact 授权分页、离线/过期错误、留存配额、结构化结果 | 文件访问与输出策略负例；限额不死锁；mutation coverage 不冒充完整 |
| W12 | P5：打包、全套验收、迁移和一致性备份恢复、客户端全流程、干净环境安装 | 候选发布包、A01–A16 证据、客户端兼容记录、安装和排障文档 |
| W13 | 修复验收缺陷、受影响回归、首发检查和必要缓冲 | 达标则发布 v0.0.1；未达标则保留候选状态并重排后续 |

### 7.3 发布必须自带的文档

README 快速开始、Server/Node 配置样例、MCP 客户端配置、审批与取消说明、UNKNOWN 排障流程、资源版本准备方法、产物与日志限制、备份恢复、协议/schema 兼容、已知限制和发布说明。

文档里的命令必须在干净环境实际执行。快速开始可以以“五分钟内跑通”为体验目标，但发布说明使用测得的步骤和时间，不把预设目标写成已达成结果。

### 7.4 首版发布门槛

全部 A01–A16 要求通过，或明确记录某一平台的适用边界；不能通过“不适用”跳过首发 Linux 的核心检查。一个真实 MCP 客户端必须完成发现、提交、等待审批、查询、产物读取和取消。

任何可复现的重复启动、授权绕过、文件 API 越界、状态丢失、取消虚报或无界资源消耗问题，都阻止首发。功能少于预期可以继续缩减便利功能，不能删除这些执行底线。

### 8.3 月底验收

不为改善试用演示自动加入 Web UI、Windows Node 或代码同步。若试用显示当前目标群体不需要该产品，记录结论并重新评估方向，不能用更多功能掩盖缺少需求。

### 9.1 目标

验证系统运行一段时间后仍能被理解和维护，尤其是输出留存、磁盘占用、重复连接、升级、恢复与未知执行处理。

### 9.2 每周任务

| 周 | 工作包 | 可检查产出 |
| --- | --- | --- |
| W18 | 多轮连接/断线、执行/取消、日志截断与留存；观察内存、句柄、磁盘 | 有场景、版本和资源曲线的报告；检查持续增长和残留 |
| W19 | 从已发布版本升级；临时目录迁移；停机一致性备份与恢复；不兼容配置检查 | 升级/恢复步骤、失败提示、可恢复数据与已知限制 |
| W20 | 演练丢确认、离线取消、token 撤销、Node 重装和 UNKNOWN 人工排障 | 不删除 journal 伪造成功；身份更换和残留清理流程可照做 |
| W21 | 基于维护证据局部重构；依赖检查；必要补丁 | 重构保留行为和协议，测试与文档同时更新 |

### 9.3 默认值与测量

以下继承实施规划作为测试起点，不是已验证的性能承诺。

| 参数 | 初始值或规则 | 要验证的行为 |
| --- | --- | --- |
| 心跳 / 离线判断 | 10 秒 / 30 秒 | 以 Server 接收时间判断，重连后先对账 |
| 运行 timeout | 默认 120 秒、上限 1 小时 | Node 可更严格，断线不关闭 timeout |
| 审批有效期 | 10 分钟 | 过期不执行，审批不消耗运行 timeout |
| 请求防重窗口 | 30 天 | 保留期内状态清理不破坏幂等；删除状态的限制明确 |
| 单次返回/读取 | 64 KiB | 分页与截断可解释，不把所有日志塞给模型 |
| 单执行日志 | stdout/stderr 合计 10 MiB | 达限后继续排空，控制内存和磁盘 |
| Node 产物预算 / 日志留存 | 1 GiB / 7 天 | 不删运行中日志，不顺带删除未确认 journal |
| 协议帧 / 产物分块 | 1 MiB / 至多 64 KiB | 超限拒绝，产物读取不阻塞心跳与取消 |

调整默认值时记录触发场景、取舍和受影响测试，不能仅为让某一次 Demo 成功无限放宽配额。

### 9.4 月底验收

至少完成一次已发布版本升级/恢复演练和一次完整故障排障演练；长期运行检查记录实测时长与负载，不能用短时测试宣称长期稳定。未解决的持续资源增长或恢复缺陷必须进入阻塞清单。

## 10. 第 6 月：交接、发布质量与下一步决策

### 10.1 目标

让项目具备可持续维护的基本条件，并依据半年证据决定继续打磨或进入下一种能力，而不是机械推进预设的大架构路线。

### 10.3 扩展决策门槛

| 候选方向 | 需要先观察到什么 | 必须承担的新增成本 |
| --- | --- | --- |
| 自有 Agent / Web | 用户持续需要 RunWeave 自身负责交互与任务推进 | 模型接入、上下文、任务状态、审批交互和新的测试面 |
| Windows Node | 真实用户的核心资源在原生 Windows，Linux/WSL 无法满足 | 进程树、路径、文件边界、服务与打包测试 |
| 新操作或沙箱 | 现有明确操作无法满足实际任务，或需要运行不可信代码 | 独立操作语义、结果契约和隔离验证 |
| 多 Server / 新数据库 | 有可重复的吞吐或可用性瓶颈 | 一致性、分布式租约、迁移、运维和故障复杂度 |
| 任务图 / 自动恢复 | 出现明确依赖、重试和补偿需求 | 幂等策略、重试语义、补偿与恢复证明 |

这些是选择条件，不是第六个月必须实现的功能清单。下一阶段原则上只选一个主要方向；更大的路线可保留为愿景。

每项证据记录日期、commit、二进制/协议/schema 版本、操作系统、客户端版本、前置配置、操作步骤、预期、实际、日志位置和结果。未完成项标记未验证，不用“应该通过”替代记录。

placement 使用固定快照与表驱动测试；协议使用 JSON fixture；执行生命周期使用真实子进程；持久性使用临时数据库和进程重启；网络故障通过受控丢消息/断连接注入。关键副作用测试使用可观测计数器，同时承认模糊崩溃窗口只能得到 UNKNOWN。

常规检查采用 go test、适用目标环境的 race 检查、go vet、依赖漏洞检查与发布构建。普通单元测试不调用 LLM；真实客户端验收独立记录。测试服务于风险，不追求覆盖率数字或无限重复完整测试。

## 12. 每周工作方式与任务拆分

周初选一个可验证结果并写清楚失败条件；开发中逐步完成该路径；周末保留 Demo、测试证据、已知问题及下周依赖。遇到边界决策写短记录，避免在聊天中决定后无人更新文档。

每个开发任务至少包含：具体问题、范围、输入/输出或状态变化、验收方式、依赖、预计工作量。大任务拆成能在数日内验证的增量，不能用“完成 Runtime”作为一个月不可检查的任务。

AI 可用于实现、测试场景、代码审查和文档同步；真实环境确认、权限边界、错误语义和发布判断必须有可核查证据。此计划不要求多 Agent 并行开发。

没有真实第二种实现时不创建通用框架。重构必须能说明减少了哪种重复或耦合，并确保协议和持久状态行为不发生无意变化。

## 13. 风险、缓冲与范围调整

| 风险信号 | 应对 | 不能采用的捷径 |
| --- | --- | --- |
| MCP 客户端不会稳定轮询或生成合法请求 | 改善 schema、描述、错误和示例；锁定可验证客户端 | 把 SDK 自测当成产品接入成功 |
| 进程崩溃与取消语义迟迟不清楚 | 收紧前台作业边界，先验证真实进程回收与 UNKNOWN | 只 kill 父进程后宣称任务已停止 |
| 跨节点 Demo 依赖最新代码同步 | 预准备明确 revision，版本不符拒绝 | 暗中复制文件却宣称不需要同步 |
| 配置与审批太繁琐 | 改善示例、诊断、可信项目显式策略 | 默认允许所有代码执行 |
| 首版超过第 13 周 | 挪用后半程缓冲、减少便利功能，重新排期 | 砍掉幂等、授权、超时或故障测试 |
| 多数问题来自安装和日志 | 优先修复这些问题 | 转而开发 Agent、Web 或插件平台 |
| 无外部试用者或无重复使用 | 如实标记证据缺失，项目所有者调整验证方式 | 将内部 Demo 当作市场验证 |
| 出现新平台或企业需求 | 记录候选范围与成本，另行排序 | 直接加入当前首发承诺 |

可优先延后的项目包括更漂亮的 CLI 展示、额外客户端、Windows CLI 便利支持、非核心解析器和额外报表。六个 MCP 工具及实施规划中的基础产物读取若要移出首版，需要明确修订范围；不能仍按原验收宣称全部完成。
